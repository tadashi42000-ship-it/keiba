# 一般公開・課金収益化に向けたハードルと回避策（調査メモ）

> 作成日: 2026-06-10 / 調査ベース。法的判断の最終確認は必ず専門家（弁護士・税理士）に依頼すること。
> このメモは「個人利用の研究ツール」を「不特定多数向けの有料サービス」に転換する際の論点整理。

## TL;DR（結論）

現状アプリの最大の障壁は **(1) データソースの規約違反リスク（netkeiba/Umanityのスクレイピング商用利用）** と **(2) 競馬予想を有料提供する事業者規制（特商法・景表法）** の2つ。技術・課金は解ける問題だが、この2つは「設計そのものを変えないと回避できない」構造的ハードル。

| # | ハードル | 深刻度 | 回避可能性 |
|---|---|---|---|
| H1 | スクレイピングデータの商用利用（規約・著作権） | ★★★ 致命的 | 設計変更で回避可（データソース差し替え） |
| H2 | 競馬予想の有料提供に対する事業者規制 | ★★★ 重大 | 運用ルールで回避可（表記・表現の統制） |
| H3 | AI/外部APIの商用コスト・規約 | ★★ 中 | 課金設計で吸収可 |
| H4 | インフラ常時稼働・スケール | ★★ 中 | クラウド移行で解決 |
| H5 | 決済・特商法表記・税務 | ★ 低 | 手続きで解決 |
| H6 | 免責・ギャンブル依存・炎上リスク | ★★ 中 | 規約・UIで緩和 |

---

## H1. データソース（スクレイピング）の商用利用 ★★★

### 問題
本アプリは `get_keiba_info.py` / `race_catalog.py` / `same_day_sources.py` で **netkeiba.com を全面スクレイピング**している。netkeiba 利用規約には次の趣旨が明記されている（[netkeiba利用規約](https://support.keiba.netkeiba.com/hc/ja/articles/18854650196121-netkeiba-%E5%88%A9%E7%94%A8%E8%A6%8F%E7%B4%84)）:

- サービスを通じて入手したデータは「**著作権法で認められた私的利用の範囲を超える複製・販売・出版**」に利用できない。
- 著作物に該当しないデータでも「**サービスを通じて入手したものは著作物とみなす**」。
- スクレイピングで負荷をかけると[通信制限の対象](https://support.keiba.netkeiba.com/hc/ja/articles/18841959592857)（解除依頼にも応じない場合あり）。

→ **有料サービスとしてnetkeibaのデータを再配信するのは規約違反かつ著作権侵害リスクが高い。** 個人研究の範囲（=現状）だから黙認されているにすぎない。Umanityも同様。公開・課金した瞬間に「私的利用」の言い訳が消える。

### 回避策
1. **【本命】JRA-VAN DataLab. の正規データに差し替える**
   - 月額 2,090円（税込）の会員制データAPI（[JV-Link](https://jra-van.jp/dlb/sdv/)）。30年分のレース成績・血統・ラップ・通過順・払戻を機械可読で提供。
   - **商用利用は別途許諾が必要**。アプリ販売は事前相談必須（[開発者コミュニティ](https://developer.jra-van.jp/)）。
   - 一般的なモデル: 「**有料シェアソフト方式 = エンドユーザー各自がDataLab.を契約**」していれば配布可。つまり「データはユーザーが自分の契約で取得、アプリは加工・表示UIを提供」という建付けにすれば正規化できる。
   - 地方競馬は **NAR/楽天競馬系の「地方競馬DATA」** など別契約が必要。
2. **【次善】提携・データ購入**: netkeiba運営（株式会社ネットドリーマーズ→現 LINEヤフー系）や他データ提供業者と商用ライセンス契約を結ぶ。コスト・交渉ハードルは高いが「規約上クリーン」。
3. **【UI/ツール特化で逃げる】**: 自前でデータを再配信せず、「ユーザーが入力・取得した情報をAIで整理するツール」に再定義。データ取得はユーザー側の責任に寄せる（ただしUXは落ちる）。
4. **AI解析対象の二次情報（YouTube概要欄・Web記事）** は各プラットフォームのAPI/規約に従う限り比較的グレーが薄いが、引用元明示と要約に留める。

> 実務上の最有力 = **JRA-VAN DataLab.の商用許諾を取り、データ取得はユーザー契約ベースにする**。これでH1の核は解消する。

## H2. 競馬予想を有料提供する事業者規制 ★★★

### 問題
「競馬予想の有料提供」自体に**特別な営業許可・免許は不要**（公営競技の予想は風営法等の対象外。参考: [弁護士ドットコム/OKWAVE議論](https://okwave.jp/qa/q3842612.html)）。ただし**消費者向け有料情報サービス**として以下が全面適用される（[IT弁護士 中野氏 解説](https://it-bengosi.com/blog/)、[ホースメン会議 特商法表記例](https://www.hmco.jp/law.html)）:

- **特定商取引法**: 事業者名・住所・電話番号・代表者・料金・支払方法・返品/解約条件のサイト明記が**義務**。誇大広告・不実告知は行政処分対象。
- **景品表示法 / 消費者契約法**: 「**100%的中**」「**絶対当たる**」「**必ず利益**」等の断定的表現は違反。的中率・回収率・利用者の声は**客観的根拠が必須**（架空の口コミはアウト）。
- 競馬予想サイトは**詐欺的業者が社会問題化**しており（[消費者庁・弁護士ドットコム記事多数](https://www.bengo4.com/c_1009/n_11682/)）、当局・世論の目が厳しい業種。

### 回避策
1. **特商法表記ページを必須実装**: 個人なら屋号+本名+連絡先開示が必要（自宅住所を晒したくない→**バーチャルオフィス**や**法人化**で回避）。
2. **広告・UI表現ガイドラインを社内策定**: 「予想」「参考情報」と明記し、的中保証・煽り文言を全面禁止。実績表示は「過去N走の検証データ（取得日明記）」のように検証可能な形のみ。
3. **法人化（合同会社など）**: 個人情報露出回避・税務・信用面で有利。設立費用は合同会社で約6万円〜。
4. **利用規約・免責で「投資勧誘ではない」明示**（→H6と連動）。
5. **返金・解約フローを明確化**（サブスクならクーリングオフ不適用だが、解約導線の明示は特商法上の必須）。
6. **開業届/事業所得の確定申告**（課金が事業所得になる）。インボイス登録要否も検討。

## H3. AI・外部APIの商用コストと規約 ★★

### 問題
ユーザー数に比例してAPIコストが線形増加。各APIには無料枠・規約・レート制限がある。

| API | 商用可否 | 注意点 |
|---|---|---|
| **Gemini API** | 無料枠も商用OK（[Google AI pricing](https://ai.google.dev/gemini-api/docs/pricing)） | 無料枠はRPM/RPD制限が厳しく**本番不可**。2026/4〜Proモデルは無料枠から除外、有料はpay-as-you-go+月額上限。**無料枠はデータ学習に使われる**ためユーザーデータ投入は有料枠必須。 |
| **YouTube Data API** | 規約準拠なら可 | 1日10,000ユニットの無料クォータ。検索は1回100ユニット=**1日100検索で枯渇**。スケール時は申請で増枠 or 有料化。 |
| **Tavily / X API** | 従量課金 | X APIは$0.008/tweet等、利用量で高騰。 |

### 回避策
1. **有料枠 + 月額スペンドキャップ**で青天井を防止（Geminiは上限到達で自動停止）。
2. **キャッシュ徹底**: 既に`data/`へキャッシュ実装あり。レース単位で結果を共有し、**ユーザーごとに再生成しない**設計に（同一レースは全ユーザー共通結果）。これでAPIコストを「ユーザー数×」から「レース数×」に圧縮できる = **収益化の肝**。
3. **重い処理はバックグラウンドで事前生成**（`scripts/run_same_day_updater.py`の発想を全レースに拡張）。リアルタイムAPI叩きを排除。
4. **モデル選択の最適化**: 解析は`gemini-flash-lite`系で十分な箇所を切り分けコスト削減。
5. **無料枠ユーザーへの機能制限**（フリーミアム）でAPI消費を有料ユーザーに集約。

## H4. インフラ常時稼働・スケール ★★

### 問題
現状は**ローカルPC + ngrok/Cloudflareトンネル**運用（`scripts/start_mobile_pwa.ps1`）。PCを切ると死ぬ。不特定多数には耐えられない。Streamlit版はさらにシングルセッション前提。

### 回避策
1. **フロント（Next.js/PWA）= Vercel**、**バックエンド（FastAPI）= Render/Railway/Fly.io or Cloud Run** へ移行（M5マイルストーンで着手済み）。
2. **データ/キャッシュ層**: ファイルキャッシュ(`data/`)→ クラウドDB（Supabase/Postgres）or オブジェクトストレージへ。
3. **スクレイピング常駐をジョブ化**: 定期バッチ（Cloud Scheduler/cron）でレースデータを事前取得・キャッシュ。ユーザーリクエスト時はDB読むだけ。
4. **legacy Streamlit版は社内/個人用に隔離**し、公開対象はNext.js/PWA版に一本化。
5. レート制御・WAF・bot対策（公開すると自分が叩かれる側になる）。

## H5. 決済・特商法表記・税務 ★

### 問題
課金には決済基盤と各種表記・税務処理が必要。

### 回避策
1. **決済**: Stripe / PAY.JP（サブスク対応）。アプリストア配信ならApple/Google課金（手数料15-30%）。PWA配信ならWeb決済でストア手数料を回避可。
2. **特商法表記**（H2と重複）/ **プライバシーポリシー**（個人情報・Cookie・解析ツール利用の明示）を必須設置。
3. **インボイス制度**対応（課税事業者になるか、適格請求書発行事業者登録の要否）。
4. **資金決済法**: 前払式支払手段（ポイント制）にすると規制が増えるので、**都度課金 or サブスク**にして回避。

## H6. 免責・ギャンブル依存・レピュテーション ★★

### 問題
予想が外れる→クレーム/返金要求/炎上。競馬予想業界は詐欺イメージが強く、信用構築が難しい。賭博助長の社会的批判リスク。

### 回避策
1. **利用規約に免責明記**: 「予想の的中・利益を保証しない」「投資・賭博の勧誘ではない」「自己責任」。
2. **18歳未満（馬券は20歳以上推奨）の利用制限**・年齢確認導線。
3. **依存症への配慮表示**（公営競技の標準。「のめり込みに注意」+相談窓口リンク）。
4. **断定表現の排除**（H2と連動）。「AIによる参考情報」というスタンスを一貫。
5. **透明性で差別化**: 「なぜこの評価か」の根拠（本アプリの強み=メリット/デメリット可視化）を出し、ブラックボックス詐欺サイトとの違いを明確化。

## 推奨ロードマップ（優先順）

1. **【最優先・前提】H1: データソースの正規化判断** — JRA-VAN商用許諾の事前相談 or データライセンス交渉。ここが通らないと公開できない。スクレイピング前提のままの公開は不可。
2. **H2/H5/H6: 法務・規約・表記の整備** — 特商法表記、利用規約、免責、プライバシーポリシー。法人化検討。**弁護士レビュー必須**。
3. **H4: インフラのクラウド常時稼働化** — Vercel + Cloud Run + DB。スクレイピング/AI解析をバッチ事前生成へ。
4. **H3: APIコスト設計** — レース単位の共有キャッシュでコストをユーザー数から切り離す。フリーミアム設計。
5. **H5: 決済導入** — Stripe/PAY.JPでサブスク。
6. ベータ公開 → フィードバック → 段階的に課金開始。

---

## 一言まとめ
> **「技術的には作れているが、`データの出どころ` と `予想を売る事業者としての責任` を正規化しないと売ってはいけない」** という状態。
> 逆に言えば、**JRA-VAN正規データ + 法務整備 + クラウド化 + 共有キャッシュ**の4点を押さえれば、本アプリの強み（AI×多ソース横断のメリデメ可視化）はそのまま商品になる。
